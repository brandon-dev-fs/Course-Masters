# Backend Plan: Profile Page Modernization

## Overview

Add a `themePreference` field to the `User` model and expose two new endpoints: `GET /api/users/me` (return authenticated user profile) and `PATCH /api/users/me/preferences` (update theme preference). Both endpoints operate on the authenticated user only — no admin or ownership middleware required beyond `authenticate()`.

## Schema Changes

### New field on `User` model

Add a nullable `themePreference` column to the existing `User` model in `server/prisma/schema.prisma`:

```
themePreference String? @map("theme_preference")
```

- **Type**: `String?` (nullable). Null is treated as `"system"` by the client.
- **Position**: after the `banExpires` field, before `createdAt`.
- **No enum**: The field stores `"light"`, `"dark"`, or `"system"` as plain strings. A Prisma enum is unnecessary since the values are validated by Zod at the API boundary and the client treats null as `"system"`.
- **No default**: Null default is implicit for optional fields. Existing users will have `null` (equivalent to "system").

### Migration

Generate with:

```
npx prisma migrate dev --name add_theme_preference_to_user
```

This is a purely additive change (new nullable column) — no expand-contract phases needed. No data migration required. Existing rows get `null` automatically.

After migration, run `npx prisma generate` to update client types.

## New Endpoints

### GET /api/users/me

Returns the authenticated user's profile data.

**Layer structure:**

- **Route**: Add `router.get('/me', userController.getMe)` to `user.routes.ts`. Must be registered **before** the `/:userId` route to avoid `me` being captured as a `userId` param.
- **Controller**: `userController.getMe` — extracts `req.user!.id`, calls `userService.getMe(userId)`, returns `res.json(profile)`.
- **Service**: `userService.getMe(userId)` — queries `prisma.user.findFirst` with `where: { id: userId, deletedAt: null }` and `select: { id, name, email, role, themePreference, createdAt }`. Throws `NotFoundError` if null (defensive — should not happen for an authenticated user).

**Auth**: `authenticate()` only (inherited from router root). No `authorize()` — all roles can access their own profile.

**No validation needed**: No request body or query params.

### PATCH /api/users/me/preferences

Updates the authenticated user's theme preference.

**Layer structure:**

- **Route**: Add `router.patch('/me/preferences', validate(updatePreferencesSchema), userController.updatePreferences)` to `user.routes.ts`. Must also be registered before `/:userId`.
- **Controller**: `userController.updatePreferences` — extracts `req.user!.id` and `req.body`, calls `userService.updatePreferences(userId, body)`, returns `res.json(result)`.
- **Service**: `userService.updatePreferences(userId, data)` — runs `prisma.user.update({ where: { id: userId }, data: { themePreference: data.themePreference }, select: { themePreference: true } })`. Returns the updated preference value.

**Auth**: `authenticate()` only. No `authorize()` — all roles can set their own preference.

**Validation**: Zod schema at route boundary (see below).

## Validation

### New schema file: `server/src/schemas/user.schema.ts`

```ts
// updatePreferencesSchema
{
  themePreference: z.enum(["light", "dark", "system"])
}
```

Export both the schema and the inferred type.

The `z.enum` ensures only valid values reach the service layer. Invalid values return 400 with `VALIDATION_ERROR` and field-level details.

## Error Handling

Both endpoints use existing error infrastructure:

| Scenario | Error class | Code | Status |
|---|---|---|---|
| User not found (GET /me — defensive) | `NotFoundError` | `NOT_FOUND` | 404 |
| Invalid themePreference value (PATCH) | `ValidationError` (via `validate()` middleware) | `VALIDATION_ERROR` | 400 |
| Missing/expired session | `authenticate()` middleware | `UNAUTHENTICATED` | 401 |

No new error classes or codes are needed.

- `server/src/routes/index.ts` — user router is already mounted at `/users`.
- Middleware — no new middleware required; existing `authenticate()` covers both endpoints.
- Error classes — existing classes suffice.

## Migration Notes

- The migration adds a single nullable `VARCHAR` column. This is a non-blocking `ALTER TABLE ADD COLUMN` in PostgreSQL — safe for production with zero downtime.
- No seed data update is needed. Existing users will have `themePreference = null`, which the client interprets as `"system"`.
- No backfill is required.
